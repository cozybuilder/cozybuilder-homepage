# PROGRAM OPERATING MODEL — CozyBuilder 홈페이지·프로그램 운영 구조

## 1. 홈페이지의 역할

CozyBuilder 홈페이지는 단순 회사 소개 사이트가 아니라 다음 기능을 담당하는 중앙 플랫폼이다.

- CozyBuilder 브랜드 허브
- 공통 회원가입·로그인
- 무료 프로그램 유입
- 프로그램 탐색·소개
- 마이페이지의 내 프로그램 통합 조회
- 무료 이용·무료 체험·구독·구매 상태 표시
- 유료·독립 서비스의 실행 진입점
- 프로그램별 이용·전환 분석

홈페이지 자체의 입장료나 일괄 구독을 기본 수익모델로 삼지 않는다. 사용자는 필요한 유료 프로그램에만 개별 결제한다.

## 2. 두 가지 운영 모델

### A형 — 홈페이지 귀속형

무료이거나 작고 단순한 프로그램을 홈페이지 내부에 귀속한다.

적합 조건:

- 무료 제공이 핵심인 프로그램
- 회원 유입과 재방문을 만드는 미끼 상품
- 독립 브랜드가 필요하지 않음
- 별도 서버·고비용 AI API·복잡한 결제가 없음
- 홈페이지 저장소에서 빠르게 구현·운영 가능
- 별도 배포보다 홈페이지 내부 편입이 효율적

구조:

- URL: `cozybuilder.co.kr/programs/...` 또는 홈페이지 내부 앱 경로
- 홈페이지 인증·세션을 그대로 사용
- 마이페이지의 `내 프로그램`에 자동 표시
- 홈페이지 분석·권한 체계를 그대로 사용
- 무료 이용 상태로 관리

목적:

무료 프로그램 사용을 위해 사용자가 CozyBuilder 계정을 만들고, 마이페이지에서 다른 무료·유료 프로그램을 발견하도록 한다.

### B형 — 독립 서비스형

유료 SaaS, 자체 데이터와 운영비가 있는 프로그램, 독립 성장 가능성이 있는 서비스를 별도 프로젝트로 운영한다.

적합 조건:

- 자체 상품명·고객·요금제가 있음
- 결제·구독·AI API·파일 업로드·비동기 작업이 있음
- 민감하거나 대량의 업무 데이터를 저장함
- 홈페이지와 독립적으로 자주 개발·배포해야 함
- 독립 브랜드·도메인·매각 가능성이 있음
- 홈페이지 저장소에 포함하면 복잡도와 장애 영향이 커짐

구조:

- 별도 GitHub 저장소
- 별도 배포와 서브도메인 또는 독립 도메인
- CozyBuilder 공통 계정의 사용자 ID를 사용
- 서비스 업무 데이터는 서비스별로 분리
- 홈페이지 마이페이지에서 이용 상태와 실행 버튼 제공
- 프로그램별 개별 결제·구독

홈페이지는 서비스 본체를 품지 않고 소개·로그인·권한·구독 상태·실행 연결을 담당한다.

## 3. 마이페이지 상태 모델

마이페이지의 상위 명칭은 `내 프로그램`으로 한다.

표시 상태:

- 무료 이용 중
- 무료 체험 중
- 구독 중
- 구매 완료
- 이용 종료

A형과 B형 모두 같은 목록에 표시한다. B형의 실행 버튼은 외부 서비스 URL로 이동한다.

## 4. 공통 로그인 원칙

- 프로그램마다 별도 회원 DB를 만들지 않는다.
- 홈페이지가 사용하는 공통 인증 공급자와 사용자 ID를 재사용한다.
- 각 독립 서비스는 필요한 콜백 URL과 인증 클라이언트 설정만 추가한다.
- 완전한 서브도메인 간 SSO는 필요 시 중앙 인증 리디렉션 또는 공통 세션 구조로 확장한다.
- 통합 대상은 사용자 신원과 이용권이며, 서비스 업무 데이터는 분리한다.

## 5. 결제·구독 원칙

- 홈페이지 회원가입은 무료다.
- 홈페이지 전체 이용을 조건으로 한 강제 구독은 두지 않는다.
- 유료 프로그램은 프로그램별 요금제로 결제한다.
- 여러 프로그램을 묶는 통합 구독은 충분한 유료 상품과 실제 수요가 생긴 뒤 검토한다.
- 마이페이지에서는 모든 프로그램의 이용권·구독 상태를 통합 조회한다.

## 6. 신규 프로그램 판정 절차

신규 프로그램 시작 전 아래를 판단한다.

1. 무료 유입 상품인가, 독립 유료 상품인가?
2. 별도 운영비·AI API·결제·민감 데이터가 있는가?
3. 독립 배포와 잦은 업데이트가 필요한가?
4. 독립 브랜드와 URL이 유리한가?
5. 홈페이지 저장소에 포함할 경우 복잡도가 과도하게 증가하는가?

판정:

- 무료·소형·저비용·홈페이지 유입 목적이면 A형
- 유료·대형·독립 운영·별도 데이터가 필요하면 B형
- 애매하면 MVP는 A형으로 시작할 수 있으나, 분리 비용이 예상되면 처음부터 B형으로 한다.

## 7. 현재 적용

### A형 유지 후보

- 홈페이지 내부의 기존 무료 프로그램
- 전자책 만들기
- ClipMiner 웹 기능

기존 프로그램은 즉시 이전하거나 폐기하지 않는다. 현재 구조를 보존하고 실제 사용 반응을 기준으로 추가 개발 여부를 판단한다.

### B형 기본 적용 후보

- 코지임대
- 평생사진관
- AI Promotion
- 향후 유료 SaaS와 독립 서비스

## 8. 운영 원칙 요약

> 무료 프로그램은 홈페이지에 귀속해 회원 유입과 교차 노출에 사용한다. 유료·대형 서비스는 독립 배포하되, 공통 로그인과 마이페이지를 통해 하나의 CozyBuilder 생태계로 연결한다.

## 9. 프로그램 배포 상태 (deploy_status)

프로그램(programs 테이블)은 명시적 배포 상태를 갖는다. (migration 0014)

| 상태 | 코드값 | 카드 배지 | 상세 화면 CTA |
|------|--------|-----------|----------------|
| 사전신청 | `preregistration` | 사전신청 | "사전신청하기"(문구 변경 가능) → 사전신청 랜딩 URL 이동. 스토어·실행 버튼 미노출 |
| 출시됨 | `released` | (없음 — 기존 규칙) | 기존 로직 유지: web=구독/실행, mobile=스토어 URL 존재로 출시 추론(Release Model v3) |
| 준비 중 | `preparing` | 준비 중 | 클릭 불가 "준비 중" 표시. 스토어·사전신청 버튼 숨김 |
| (null) | 레거시 | released 와 동일 | released 와 동일 — 기존 데이터 무변경 원칙 |

### 사전신청 필드

- `prereg_url` (사전신청 선택 시 필수): 내부 경로(`/landingpage/cozyrent`) 또는 `https://` URL 만 허용.
  `javascript:` 등 기타 scheme 차단, 공백 정규화. 내부 경로 저장을 우선한다.
- `prereg_cta_label` (선택): 버튼 문구. 비우면 기본 "사전신청하기".
- `prereg_benefit` (선택): CTA 아래 혜택 문구.

### 출시 전환 절차 (코드 수정 없이 관리자 설정만으로)

1. 관리자 → 프로그램 수정 → 배포 상태를 "사전신청" → "출시됨"으로 변경.
2. Google Play URL / App Store URL 입력(웹이면 실행 URL).
3. 저장 → 카드·상세가 자동으로 스토어 버튼 구조로 전환.
- 사전신청 랜딩 URL 은 출시 후에도 DB 에 보존되지만(숨김 input 으로 유지),
  출시됨 상태에서는 CTA 로 노출하지 않는다.

### 관리자 입력 규칙

- 상태별로 해당 없는 입력란은 숨긴다(숨겨진 값은 hidden 으로 보존 — 상태 전환 실수로 URL 이 지워지지 않게).
- released 상태의 web/mobile 플랫폼 전환 시 반대편 링크 정리는 기존 동작 유지.

## 10. 프로그램 상세페이지 `/programs/[slug]`

### 역할

- `/programs/[slug]` = 프로그램의 **상시 제품 홍보·전환 상세페이지**다. 방문자가 제품 필요성을
  이해하고 신뢰한 뒤 설치·실행까지 결정하도록 만드는 것이 목적이다.
- `/landingpage/[slug]`(사전신청·캠페인·신청폼 플랫폼 — [LANDINGPAGE_PLATFORM.md](../landing/LANDINGPAGE_PLATFORM.md))와
  **역할이 다르며 서로를 대체하지 않는다.** 두 구조는 계속 별도로 유지한다.

### 설득 흐름(고정 순서)

HERO → 문제 공감 → 해결·핵심 가치 → 실제 화면 → 추천 대상 → 신뢰 지표 → 제작 배경 →
실제 후기 → 이용 안내 → FAQ → 최종 CTA → 업데이트 내역

### 선택 마케팅 데이터 — `landing_content`

- 홍보용 선택 콘텐츠는 개별 컬럼을 늘리지 않고 **`programs.landing_content jsonb` 한 곳**이 소유한다
  (migration 0016 · nullable). 구조·검증 SSOT는 `lib/program-landing.ts`(`version: 1`).
- 서버가 저장·조회 양쪽에서 정규화한다. 잘못된 값·레거시 값·`null` 이어도 **기존 프로그램 데이터로
  정상 렌더**되어야 하며, malformed 값이 공개페이지를 깨뜨리지 않는다.
- v1은 **일반 문자열만** 받는다. HTML·Markdown 입력을 허용하지 않는다.

### 표시 규칙

- **데이터가 없는 선택 섹션은 섹션 전체를 숨긴다.** 빈 카드·빈 제목·placeholder를 노출하지 않는다
  (screenshots 0장·updates 0건도 동일).
- **실제 근거가 있는 후기·수치만 표시한다.** 사용자 수·후기·별점·사용 사례·앱 화면을 코드에서
  생성하거나 자동 추정하지 않는다. 기본값은 비어 있음이다.
- 핵심 가치(`benefits`)가 비어 있으면 기존 `features`를 주요 기능으로 표시해 기존 데이터 의미를 유지한다.

### 변하지 않는 것

- 실행·구독·스토어·`deploy_status`의 의미와 동작은 **기존 정책(§9·Release Model v3)이 계속 소유**한다.
  `landing_content`는 **문구만** 담고 이동 목적지·권한을 소유하지 않는다.
- CTA의 실제 목적지는 종전대로 `play_store_url`·`app_store_url`·`app_url`·`prereg_url`·앱 접근 권한이 정한다.
- 가격·체험 기간 등 정책 수치는 이 페이지가 SSOT가 아니다. 제품별 정책 문서가 소유한 값을 문구로 옮길 뿐이다.
- 목록·메인 카드 썸네일은 종전대로 `image`만 사용한다.

## 11. 실제 화면 (screen stories)

프로그램 상세의 `실제 화면` 섹션 — 앱 캡처 한 장과 그 화면의 제목·설명을 한 세트로 보여준다.

### 소유 구조

새 컬럼·migration 없이 기존 두 값이 나눠 소유한다.

| 소유 | 내용 |
|---|---|
| `programs.screenshots` | 실제 화면 이미지 URL 배열 **+ 표시 순서** |
| `programs.landing_content.screenStories` | 같은 순서의 `{ title, description, visible? }` |

- 두 배열은 **표시 순서로 1:1 대응**한다 — `screenshots[i]` ↔ `screenStories[i]`.
  노출을 끈 화면도 저장 배열에서 빼지 않는다(빼면 다시 켤 때 짝이 깨진다).
- 이미지 URL을 `screenStories` 안에 **중복 저장하지 않는다.**
- **최대 20개**(`MAX_SCREEN_STORIES`). 상한은 `lib/program-screen-story.ts`가 단독 소유하고
  관리자 UI·서버 저장·정규화가 같은 값을 쓴다.
- `landing_content`의 `version`은 **1 그대로**다. `screenStories`는 optional 이라 기존 데이터가 그대로 읽힌다.
- 짝짓기·표시 판정·관리자 저장 검증의 SSOT는 `lib/program-screen-story.ts`다.

### 관리자 입력

- `/admin/programs/[id]`의 `실제 화면` 섹션에서 **하나의 행**으로 편집한다 —
  노출·이미지·제목·설명·순서.
- 순서 이동(↑/↓)은 네 값이 **한 행 단위로 같이** 움직인다.
- 행마다 `노출` 체크박스가 있다. **체크 해제는 삭제가 아니다** — 이미지·제목·설명은
  그대로 저장되고 공개페이지에서만 숨는다. 다시 체크하면 원래 자리로 돌아온다.
- 현재 개수를 `8 / 20` 으로 표시하고, 20개에 도달하면 추가를 막는다.
  여러 장을 한 번에 올릴 때 남은 자리보다 많이 고르면 **업로드를 시작하기 전에** 막는다
  (일부만 Storage 에 올라가는 일이 없도록).
- 제출은 두 hidden 으로 나뉜다: `screenshots`(URL 줄바꿈) · `screen_stories`(제목/설명 JSON).
- 이미지가 없는 행은 저장 대상에서 제외한다.

### 저장 규칙 — 조용한 불일치 금지

- `screen_stories`가 비어 있으면 허용한다(기존 프로그램 호환 · 공개는 기존 gallery).
  이미지만 있고 제목·설명이 전부 비어 있으면 **story 미사용**으로 본다. 노출 체크박스가
  기본 체크로 보인다는 이유만으로 사용 상태가 되지는 않는다.
- 사용한다면 `screenshots.length === screenStories.length` 이어야 하고, 각 행에 **제목이 필수**다.
- 이미지·설명 모두 **20개를 넘으면 저장하지 않는다.** UI 를 우회한 FormData 도 서버에서 막는다.
- 개수가 어긋나거나 제목이 빠지면 **조용히 저장하지 않고** 몇 번째가 문제인지 오류로 알린다.
- 최종 `landing_content`는 기존 값과 검증된 `screenStories`를 합친 뒤 `normalizeProgramLandingContent()`
  신뢰 경계를 다시 통과시킨다. 클라이언트 JSON을 그대로 저장하지 않는다.
- 두 편집기(`ProgramLandingFields` · `ProgramScreenStoryFields`)가 같은 `landing_content`의 서로 다른
  부분을 소유하므로, 한쪽만 수정해도 다른 쪽이 유실되지 않아야 한다.

### 노출 선택 — `visible`

- `screenStories[i].visible` 은 **optional** 이다. 값이 없으면 **노출(true)** 로 본다.
  기존에 저장된 데이터에는 이 값이 없으므로, 배포만으로 화면이 사라지지 않는다.
- 저장은 `visible === false` 만 남긴다(true·누락은 기본값이라 적지 않는다).
- 공개는 **이미지와 story 를 짝으로 묶은 뒤** `visible !== false` 인 짝만 거른다.
  저장 배열에서 거르지 않는다 — 거르면 index 1:1 이 깨진다.
- 공개 번호는 관리자 번호를 따르지 않고 **실제 노출되는 순서로 01부터 다시 매긴다.**
  스크롤 길이도 노출된 개수만으로 계산한다.

### 공개 표시 규칙

`lib/program-screen-story.ts`의 resolver 가 세 상태를 구분한다.

1. **story 사용 + 노출 1개 이상** → `ProgramScreenStory`
   (데스크톱: sticky 무대 + 상·중·하 3단 텍스트 레일 + 세로 기기 프레임 / 모바일: 순차형)
   - 아직 정식 데이터가 없는 레거시 상태는 fallback 문구로 같은 UI 를 쓴다(전부 노출).
2. **story 사용 + 노출 0개** → `실제 화면` **섹션 자체를 숨긴다.**
   체크를 모두 해제한 이미지를 기존 gallery 로 다시 보여주지 않는다.
3. **story 미사용** → 기존 `ScreenshotGallery`

- 레거시 fallback은 **UI 초기값**일 뿐이다. 페이지를 여는 것만으로 DB에 쓰지 않는다.
  관리자에서 저장하면 저장된 값이 항상 fallback보다 우선한다.
- 화면 개수는 고정하지 않는다. 등록한 개수만큼 그대로 표시한다.
- **실제 앱 화면만 사용한다.** 가짜 스크린샷을 만들거나 자동 생성하지 않는다.
- 비어 있는 선택 데이터는 노출하지 않는다(§10 표시 규칙과 동일).
